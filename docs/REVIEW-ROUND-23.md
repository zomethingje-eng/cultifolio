The second reviewer's fourteenth pass (three findings) and the first reviewer's round twenty-two (twenty-one findings, the grower's walk again: a hybrid edited into being, a place removed with plants in it, a name the reference does not hold, an audit, a cuttings batch, a restore onto a device that has the records but not the settings). Where both found the same thing it is listed once.

## The vault counters

1. **The object's total started from zero when KV could not be read** (R1-2, R2-6). The seed was `Number(value ?? 0)`, so a KV read that threw seeded the total at nothing and the ceiling in all counted from the deploy, not from the vaults that exist. The seed is now `null` when the read throws, and the object answers `unavailable` (a 503 with `Retry-After: 60`, "Sync could not count new vaults just now") until a read succeeds and seeds it once; the sync page shows the sentence as it is. Object test, against the real class over a fake storage: a null seed refuses, a later numeric seed is taken once and not again.
2. **The daily sweep ran from whenever the first creation happened, and a refund on the same day could go negative** (R1-3, R2-8). The alarm is set to the next UTC midnight and re-armed from there; the sweep deletes every `ip:` and `day:` key not dated today or yesterday and returns what it deleted; a refund never takes a day's count below zero. Object tests: the alarm falls at midnight, a sweep at 47 h 59 m keeps yesterday and drops the day before; refund on the day of creation.
3. **Two creations for the same key in the same instant both counted** (R2-7). `ensureVault` returns whether it created; when it did not (another request made the vault first), the count is refunded, so a race costs nothing. Route: `now` is taken once and used for the count and the refund, so a refund lands on the day it was counted.

## The collection

4. **Editing a plant into a hybrid kept the species' name, key and climate** (R2-1). The edit form now files a hybrid the way the add form does: the genus (or nothogenus) as the name, no species key, the cross as parentage, so the habitat figures and the species link go with the species the plant no longer is.
5. **Removing a place left its plants with no place and no record of the move** (R2-2). `removeLocation` moves the plants, batches and places up to the removed place's parent (or the top level), returns the counts, and writes a Move event on every plant's log ("to Porch (Cold frame was removed)"); the place page's danger text says so before, and the toast says the counts after. Unit test: the counts and the line; e2e: the toast and the plant's log.
6. **A rename left no trace** (R2-3). An edit that changes the name, the cultivar or the kind writes "Renamed from X to Y (now a hybrid)" on the log, dated today, and fills "name as received" with the old full name when it was empty. The kind is read before the write, since the record is live and says the new kind once saved (found by the e2e).
7. **A name the reference does not hold was filed on the first Add, silently** (R2-4). The first Add on an unresolved name now arms the field: the picker resolves a local exact match first (the greenhouse case, a reference name typed in full with the name service unreachable), and otherwise says "Pick a name from the list, or press Add to keep exactly what you typed"; the second Add keeps it. The plant page then carries the "Name not checked" mark beside the name, with the reason and the way to fix it. An Add clicked before a link's key has been checked against the reference waits for the check rather than filing the plant without its key. e2e: the two Adds and the mark.
8. **An audit that did not find a plant recorded nothing about it** (R2-5). Finishing an audit logs `audit` with the note "not seen" for every unticked plant (shown as "Not seen at audit" on the log), and the flash names them; `lastSeen` skips those entries and `missedAt` reports the last one, so the place's rows and the plant's Last seen card say "not seen at the audit of <date>" rather than counting a miss as a sighting.
9. **A backup holding the settings a device lacks could not be merged** (R1-1, R2-9). The preview lists the settings the file would apply ("apply the file's site, units, which this device has none of"), Merge is offered when there are settings to apply even with no fresh records or photographs, and `device.json` is validated by shape (the site as `{ lat, lon, name? }`, unrounded; preferences only when the exporting device had set one). e2e: the same file on a device with every record but no site offers Merge and applies the site.

## The formats page and its test

10. **Three of the test's checks could not fail** (R2-10). The `madeOn` line compared the function to itself; the batch name was built in the test from the same arithmetic the engine uses; the header names were literals in the test and in the routes. Now: an independent expected date from the example's stamp; `batchName`, `PUSH_HEADERS` and `listAfter` live in `$lib/sync/limits.ts`, the engine and the Worker both use them, and the test builds the name through the engine's function and reads the headers from the same constant. The test also parses and checks the record kinds, the reserved field names, the event types (against `EVENT_LABEL`), the backup's file names and paths and photo edges, `device.json`'s four keys, the legacy export's format string, the listing reply and its paging parameter (parsed by the server's own parser), the bearer header, the 507 body, the two refusal fields, the hash name and bucket count (against an FNV-1a written in the test), and that every route the page names exists. The page's template literals keep their angle brackets when the test reads it (they were being stripped as tags).
11. **The page left out `propagate` and overstated the refusals** (R2-11). `propagate` is in the event list. "Every refusal is plain JSON with an error" was not true: a refusal the sync code makes is `{ error }`, one the framework makes (a bad vault id, a missing token, a body past the limit) is `{ message }`, and a missing batch or photograph is a plain-text 404; the page says so, and the device shows whichever field the body carries (the engine reads both since round twenty-two). The 503 for uncounted creation and the 503 for a listing past what one walk can hold are named.
12. **The footers said the server sees "your vault's size"** (R2-12). Both now say "your encrypted vault, whose sizes and timing the server can see and whose contents it cannot", the settings page with a link to the formats page's paragraph on what the server can see.

## Frost

13. **The Apia comment was wrong, and the test asserted a day the arithmetic does not give** (R2-13). Solar −11 and clock +13 are twenty-four hours apart on the number line and the same hour on the clock, not "one hour apart"; 16:00 UTC is 05:00 Wednesday by the sun there and 05:00 Thursday on the clock. The comment and the test say that, and the test now checks both lines: the reader's weekday with the table's solar date in brackets, and the untouched solar line. The reviewer's fix, keeping solar wording when the raw offsets differ by more than twelve hours, was not taken: it would give the reader standing in Apia a weekday their clock disagrees with, which is the case clock time exists for; "in the table" is what marks the bracketed date as the solar row.
