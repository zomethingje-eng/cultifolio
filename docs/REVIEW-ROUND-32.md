# Round thirty-two: a walk through the deployed site

Not an outside review: a pass over `cultifolio.com` as deployed after round thirty-one's corpus, in a browser, with the network panel open, since the last two audits of the reference found things the source reviews had not. Five findings, all confirmed on the live site, all fixed here. One is the kind of thing a reader notices in the first minute.

## Found

1. **1,351 front-page tiles said "photograph did not load"** (15% of the corpus), and with them every non-iNaturalist GBIF thumbnail on the species pages, the related tiles and the sheets. GBIF's image cache stopped answering the bare address form (`image/cache/fit-in/400x/<url-encoded address>`) with `400 Image cache requests must be signed or use the occurrence API`; the occurrence form (`…/400x/occurrence/<gbifID>/media/<md5 of the address>`) answers, checked against the live cache with the Haworthiopsis attenuata photograph. The builder writes the occurrence form now; the dossier parser mends the old form as a dossier is read, using the occurrence key the photograph's id carries, so the species pages are right on deploy; the index's tile thumbnails carry no key and wait for the `--index` rebuild. MD5 is not in the Worker's WebCrypto, so it is implemented (`src/lib/dossier/md5.ts`) and held to node's own by the unit test across block boundaries. The live check now loads one GBIF-cached and one iNaturalist tile thumbnail and fails the deploy when either is not an image, which would have caught this a fortnight ago.
2. **A synonym the reference lists led to a 404.** `/species/cotyledon-paniculata` said "the name here is one the reference does not hold under any name it knows" while Tylecodon paniculatus's page said "Also known as Cotyledon paniculata". The loader asked the backbone's match service first, and that service answers a bare binomial it cannot place at a higher rank (Crassulaceae, `matchType: HIGHERRANK`), which the code rightly refuses. The index's own synonym lists (round thirty-one, 3) are consulted first, with no request; the backbone is asked only for a name the index does not carry. Unit test with the live reply.
3. **Herbarium sheets were still the photographs of some species** (Albuca yerburyi: an RBGE sheet as the hero, five Kew sheets in the grid). Round thirty filtered the GBIF media query to observations and said the bulk path already did; it does, but a species the download had no observation photographs for fell through the bulk fetcher to the network, which the offline rederive refuses, and the rederive then kept the previous build's GBIF set, from before the filter. The bulk fetcher now answers "none" for a species whose occurrences are in the download and whose multimedia has nothing, and the rederive replaces the old GBIF set with what the download says, empty included. Unit test: a species the download covers with only a sheet is "none" from the files; one the download does not hold still goes to the network.
4. **The front page said 5,523 with habitat climate; the corpus had 5,521.** The sea-cell rederive dropped two species below three land cells and the index was not rebuilt after it. `--index` after every rederive, without exception; DEPLOY.md says so.
5. **The climate paragraph counted records in cells it had left out**: "the 115 grid cells holding the 562 in-range records" on Melocactus intortus, where 22 more cells held some of those records at sea. The climate carries `seaCells` and the sentence says how the records divide.

## After the changes

`npx svelte-check --threshold warning` clean; `npx vitest run` 38 files, 383 tests; `npx playwright test tests/e2e/smoke.spec.ts --workers=1` 73 tests; the local live check's seven upstream-free checks pass. For the deployer: `npm run deploy` first (the species pages' thumbnails, the synonym lookup and the sea-cell sentence need the Worker), then the corpus step in DEPLOY.md section 5 (rederive, `--index`, both uploads) for the tiles, the sheets and the herbarium sets.
