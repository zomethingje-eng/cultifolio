# Review round eleven: the second reviewer's third pass, triaged

The second reviewer (rounds seven and eight) reviewed `ab5a1cc` (the round-eight build) against the live site on 25 September: four findings, two Lighthouse tables, an axe pass with zero violations, and a walk of the grower's paths that completed without a blocked step. Two of the four had been changed by rounds nine and ten before the review arrived; this file says what remained and what was done. One defect the author found in use is item 5.

1. **"Synced" while another device still lacked a record or photo** (R11-1, the reviewer's critical, on the evidence that the two cross-device sync tests failed on the release command twice). The two failures were real and are gone: round nine found that Playwright's "offline" did not apply to the service worker's own fetches (the test saw a synced device that was not offline), and round ten found that a device that had just joined a vault showed "Synced" for one tick before its first pull, which let the test move on before the batch had arrived. Since round ten the suite has run clean without a retry on every run, cold servers included. The protocol claim behind the finding, that `run()` has no proof its pull reached the vault's high-water mark, was checked and is answered by the cursor rather than a revision: the server lists batches by arrival time, every run lists from a minute before its cursor and skips what it holds (`OVERLAP_MS`, `have`), so a batch that arrived during or just before a run is fetched by the next one; a batch a peer sends *after* the run is, by definition, not on this device, and no revision number would make it so. What was wrong was the wording. "Synced" is a statement about a moment, and the page now says so: the status card reads "everything on the server 3 min ago is here", and the explanation on `/sync` says when the next run happens (a change made here, the app coming to the front, the connection returning, every five minutes while open, and on demand). No protocol change; the two scenarios stay in the suite as the acceptance contract.
2. **A link pairing a species with another species' key gave the plant that species' habitat** (R11-2, on `/plants/new?species=Copiapoa%20cinerea&key=8085320`). Half of this was already gone: since round ten the plant page and the labels read the species by name through the hash-bucket sheets and never by key, so the figures shown are the named species' whatever the key says, and a wrong key at species rank is repaired on the record when the sheet arrives. The other half was still there: the add and sow forms took `key` from the link on trust, so the record was saved with the wrong key and the picker's badge showed it until the plant page repaired it. Fixed at both forms (`checkedKey()` in `src/routes/plants/new/+page.svelte` and `src/routes/sowings/new/+page.svelte`): for a name at species rank the reference's own key for that name is the one kept, looked up by bucket (no name or key sent); when the reference cannot be reached or does not list the species, the key is kept as given and the plant page's repair covers it later; a name below species rank keeps its key, since the reference has none for it. e2e with the reviewer's URL shape (cinerea with humilis's key): the form shows cinerea's key, the saved record carries it, the sowing form does the same, and a subspecies keeps the key it was given.
3. **The duplicate-number repair wrote a different day in different time zones** (R11-3). Confirmed: `resolveDuplicateNumbers` stamped the renumbering note with `localDate(wall)`, so two devices merging the same collision at 00:30 UTC on New Year's Day wrote `2026-01-01` and `2025-12-31` under the same HLC, and arrival order decided which survived. The note's day is now the UTC day of the stamp, identical everywhere; the message says "batch" for a sowing number. Store test: the same collision folded under `Pacific/Honolulu` and `Pacific/Kiritimati` produces byte-identical logs, and the test fails against the old line.
4. **The plant page's mobile layout shift, CLS 0.248** (R11-4). Reproduced with a populated record at 412 × 823 under 4× CPU and 1.6 Mb/s throttling with the worker blocked (so the throttling applies): one shift of 0.205, the footer, which sat at 640 px in the server-rendered skeleton and was pushed off-screen when the record's sections arrived; and one of 0.085 when the reference answered and the "Species page" button appeared, wrapping the id card's actions to a second line. Fixed in `src/routes/plants/[acc]/+page.svelte`: the skeleton fills the first screen (`min-height: calc(100vh - 150px)`), so the footer starts below the fold; the "Species page" button's place is reserved with a hidden stand-in until the reference answers; and an own photograph's hero has a fixed height (430 px, 260 px on phones) before the pixels arrive from the vault, as the species' photograph already had. After: 0.0016 on the same run, with and without an own photograph, which is the crumb's text settling in the top bar.
5. **A species page opened from the catalogue started part-way down, below the photograph** (author, in use). Reproduced on the corpus build: the page arrived at the top and then scrolled 129 px. The section tracker on the species page calls `scrollIntoView` on the marked tab when the active section changes; on arrival a heading that is not rendered measures 0 × 0 at top 0, which counted as "passed", and `scrollIntoView` on a tab whose strip is below the fold brought the strip up, taking the page with it. The tracker now ignores headings with no height and moves the strip itself rather than calling `scrollIntoView`. Verified on the corpus build before and after (129 → 0); the e2e test that guards it uses the fixture corpus on a short screen and passes against both versions, so it is a guard, not a reproduction.
