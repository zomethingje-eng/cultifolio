# Review round fifty-three: the snapshot, the build's products, the Today tab

The round the last three reviews agreed should come next, built from the "later" list of round fifty-two: the local snapshot of the folded state (R1-25, R2-9, own E3) with the per-write index rebuilds it makes cheap to address (R1-26); the build-time search shards and catalogue windows, buckets that scale with the corpus, incremental builds and an immutable corpus manifest (R1 and R2's scaling list); and the Today tab, with the first reviewer's condition (a frost alert reachable from every tab) and the second's (unknown dates distinct from overdue). One more from the deploy: the live check that failed on a rollover. Numbers group the work: 1 is the collection on the device, 2 the reference on the server, 3 the Today tab, 4 the deploy.

## 1. The snapshot of the folded state

The load folded the whole log every time: six seconds at four hundred and fifty thousand changes, the previous reviewer measured, and every page life began with it. The fold is now kept.

1. **The order of arrival is kept** (both reviewers: fold by arrival, not by stamp). The vault has a new store, `order`, one numbered row per change stored, written in the same transaction as the change; a re-send of a change already held writes no row. A pull brings stamps older than any folded, so a snapshot taken "up to a stamp" would never be right; one taken up to an arrival number is, and what arrived after it folds on top in that order. `arrivalsAfter`, `lastArrival`, `changeKeys`.
2. **The snapshot** (`FoldSnapshot`, in meta under `fold`): the records, the fold's stamp map (`seen`, which carries the per-field stamps the incremental fold needs and the held keys), each record's first stamp, the place parent history, the latest stamp, the fold-rules version, the device, the clock correction in force, and the arrival number read before anything was read. A load reads it, folds what arrived after it, and looks through the held keys for changes that came due since (a held change comes due with no new arrival, which is why keying on the last stamp alone was never enough; own E3): those are fetched by key and folded too. The number is read first, so a change stored between the read of the number and the read of the data is folded again next time, which the fold's idempotence makes harmless, and never missed. A tail past a thousand changes writes a fresh snapshot.
3. **When it is wrong** (both reviewers' cautions, one by one): the rules version (`FOLD_RULES` in log.ts, to be bumped with any change to `apply`, the hold, the park, the required fields or `mendChange`) is not this build's; the device is another; the clock correction differs from the one it was built under (every hold was judged by the old clock; the correction's listener already rebuilds, and the rebuild writes a new one); the log was replaced (`replaceFromStaging` and `wipeVault` clear `order` and drop the snapshot in the same transaction); a stored change was displaced under its stamp (`storeIn` drops it in that transaction, since a displaced change has no inverse in a fold built on top of it). And the write itself is guarded: a counter in meta moves with every drop, the snapshot is written against the counter read before the fold was built, and the vault refuses a snapshot built against an old counter, so a tab serialising its state while another tab replaces the log cannot leave a snapshot of a log that no longer exists.
4. **What the snapshot is not.** A backup carries the log; a sync sends the log; a device without a snapshot folds the log and is the same collection. The one pass that reads every change, the one-time repair of records an old import revived, runs over the tail on a snapshot load; every device folded the whole log at least once under a build before this one, when the pass ran whole. The one-shape pass reads the fold's own stamp map instead of the changes.
5. **Per-write index rebuilds** (R1-26). The state is partitioned by kind into reactive maps beside the one map pages read records from: a derived that reads one kind's map (the plant list, the places, the batches) re-runs only when that kind changes, so a watering no longer re-sorts the plants. The per-plant event and photograph indexes are kept up to date per record touched (the old list and the new list of the plant concerned, re-sorted) rather than rebuilt from every event on every write. Another tab's write is caught up by arrival number, not by reading the whole log and filtering by what this tab has applied.
6. **The sync page says** which way this page's copy was read: the snapshot and how many changes followed it, or the whole log.

Tests: `fold-snapshot.test.ts`, on the real vault over an in-memory IndexedDB: the second load reads the snapshot and folds the tail (a stamp older than everything, arriving last; a watering; a removal) to the same state as a whole-log fold; a held change that came due since the snapshot is folded on the load that finds it due; a displaced change and a replace drop the snapshot and bump the counter, and a write against the old counter is refused; another build's rules, another device and a changed correction fold the log again; a tab catches up with another tab's writes by arrival.

## 2. The reference on the server

The Worker held the index in memory and derived everything else from it per isolate: the search's prepared structure, the entries of each bucket, nine catalogues of rows. Fifty thousand species would not fit.

1. **The build's products** (R1, R2: shards and windows at build time). `npm run dossier -- --index` writes, under `s/v2/b/<id>/` where `<id>` is a hash of the index's content: the index, the entries and the sheets of each bucket, the search split into shards by the first character of a word (an entry is in every shard one of its words begins), and the nine catalogues' rows. `src/lib/dossier/products.ts` builds them, pure; `src/lib/dossier/manifest.ts` names them.
2. **The manifest is immutable** (R2). `s/v2/manifest.json` names the id and the bucket count and hashes every file; the directory is never rewritten (a changed index is a new id), and the manifest is uploaded last, so an upload that lands in any order never names a corpus whose files are not all there, and no cache can hold one corpus's file under another's id. The Worker reads the manifest first, takes the id, the count and the index from it, and revalidates by the manifest's etag; a bucket with no manifest is read as before. DEPLOY.md has the three lines.
3. **Incremental builds** (R1). A file whose hash the previous manifest already names is left as it is, so a run whose index did not change writes nothing and `rclone copy`, which goes by size and time, carries only what changed; a run that changed a few dossiers rewrites the buckets and shards and catalogues they touch.
4. **The Worker reads by file** (`product`, a few held per isolate, cleared with the index): `/api/entries` a bucket file, `/api/search` the shard of the query's first character (`shardOf`; a first character no word in the corpus begins is nothing, with no read), `/api/rows` and the front page a catalogue file (the one opened row's species still come from the index), `/api/sheets` the sheet file under the id before the file beside the index. Each falls back to deriving from the index when the manifest names no such file. The prepared search is no longer built at load when a manifest is there; the index is the one thing held whole. The one search a sharded index does not find is a slip in the first letter of the first word, which the near pass used to forgive; said in the code and here.
5. **Buckets that scale** (R1, R2). `bucketsFor(n)`: thirty-two up to about ten thousand species, doubling past that, never more than a few hundred species a bucket; the hex name widens with the count. The build chooses the count, the manifest carries it, `/api/corpus` announces it as `buckets`, the client reads it with the id (remembered together, since a bucket name means nothing without its corpus) and hashes by it; the routes validate a bucket against the count now served. A corpus of ten thousand three hundred is served in sixty-four buckets, and `b=40` is refused under thirty-two.

Tests: `products.test.ts`: the count's steps and the names' width; every species once in the entries, every shard a word begins, the catalogues as the in-memory builder makes them, the same id for the same index; a search over the query's shard finds what a search over the whole finds, for nine kinds of query; the Worker announces id and count from the manifest and reads the index from under the id; without a manifest the etag is the id and everything is derived; with one, entries, search, rows and sheets come from the files (tampered files prove which path answered) and a missing file falls back; a corpus past ten thousand is served in sixty-four buckets. The fixture-dossier run of `--index` in a scratch tree writes eighty-four files, and a second run writes none.

## 3. The Today tab

1. **Frost is the top of Today** (the author's decision, from round fifty). The Frost tab is the Today tab, at `/today`; `/frost` is a 301 there. The page: the nine nights and the alerts as the frost page had them, then what needs you place by place in walking order (the tree, depth first, as the places are kept), each stop with the plants not watered, the plants with no watering recorded, the plants missed or unseen, and a "Water N here" that writes one dated line per plant with Undo; then the other lines the front page shows (batches in the tray, plants without a photograph, where the collection is kept). The front page's lines are unchanged in place and link to the tab's two sections.
2. **A frost alert reachable from every tab** (R1's condition). The forecast is read once per page life by a shared watch (`frost.svelte.ts`), from any page once a site is set; a risk that is not "none" is a bar under the top bar on every page but the Today tab, linking to it. A refusal is said on the front page and the Today tab, not on every page.
3. **Unknown apart from overdue** (R2's condition). A plant with no watering recorded is counted from the day its record was made, as before, but is now said so: "1 of 2 plants not watered for three weeks or more, and 1 with no watering recorded yet, its record three weeks old or more" on the front page, and two rows on the stop, "Not watered for three weeks or more (25 d)" and "No watering recorded (record 25 d old)".

e2e: the stop, the two rows, the front page's line, the bar on `/` and `/plants` going to `/today#frost`, the card and the frost row on the tab, Water here and its Undo, the old address.

## 4. The deploy

**Two builds answering is a wait, not a failure** (own, from the round-fifty-two deploy). Right after a deploy two Worker versions answer for a minute or so, and the live check's pair of requests for the species page got a rendered page of the new build and a held page of the old, which it reported as the held page differing from the rendered one. The check now reads which build each page names (the hashed entry chunk) and, when the two differ, waits five seconds and asks again, up to six times, before it judges. It also requires `/api/corpus` to announce a bucket count.
