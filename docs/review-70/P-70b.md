## 1. `r67p-pages.spec.ts:21` in WebKit: 0 asks over six loads, on both attempts

**Is a Safari grower asked? Yes.** In the same run, `r60-grow.spec.ts:465` passed in WebKit (line 1004 of the run's output). That test is about the first plant: the browser was asked once to keep the data, and its answer was said once. It wraps the browser's own `persist()` and counts the calls, so the site's ask (`keep-ask.ts`, `askToKeep`) does reach Safari's engine. The month's gate and the load's ask are the same code in every engine. Nothing in the gate depends on the engine, beyond `navigator.storage.persist` existing, and r60 14 shows it does.

**What the failing test does differently.** It puts its stand-in for Firefox's `persist()` (logged, never answered) on the object `navigator.storage` returns. r60 14 puts its stand-in on `StorageManager.prototype`.
- A property set on a DOM object is an expando on its JavaScript wrapper.
- JavaScriptCore keeps a non-node wrapper such as StorageManager's only while something holds it. Once collected, the next `navigator.storage` returns a new wrapper, without the property.
- In a loaded run, a collection between the init script and the collection's ask, seconds later, removes the stand-in. The browser's own `persist()` then answers, nothing is logged, and the count reads 0.
- Chromium keeps a wrapper that has expandos, which is why the test passes there.

This is my reading of the engine, not something I observed in it.

**Fix (the test).** `firefoxPersist` now sets both methods on `StorageManager.prototype`, as r60 14 does; a prototype is never collected. The failure message now gives both the count and `cultifolio.persistAskedAt`, so the next failure says which case it is:
- the time written but no ask logged: the stand-in was lost, as above;
- no time at all: no ask was made, which would be a fault in the code.

The test passes in Chromium three times out of three. The code is unchanged.

## 2. Flaky `smoke.spec.ts:791` in WebKit: "Receiving 4 of 4…" when the 10 s ran out

The run's call log shows the rejoin at line 877 moving through every step in turn:
- "Starting…";
- "Sending 60 of 60 changes…";
- "Checking for changes…";
- "Receiving 1 of 4…" through "4 of 4…".

It was still at "4 of 4" at 10 s. Nothing was held; the expect's wait was too short for WebKit's pace.

I counted the IndexedDB requests in Chromium with `helpers/idb-count.ts`. A first join of a vault holding 22 changes made 93 requests, and a rejoin made 139. Both took about 1.5 s. The largest transactions scale with the number of changes:
- the outbox filled with every change;
- the changes read back;
- the outbox emptied;
- the received batches stored, one get and one put a change.

This test's rejoin carries 60 changes, so about 350 to 400 requests. On the owner's PC WebKit answers one request every 16 to 20 ms (`helpers/pace.ts`), which is 7 to 8 s of IndexedDB alone, before the server's own time under a full run.

**Fix (the test).** Both joins (lines 816 and 877) now wait `writeWait(10_000, 600)`: 10 s in Chromium and Firefox, 22 s in WebKit, inside the test's 150 s. The test passes in Chromium three times out of three.

**The next run must show** that a WebKit rejoin reaches "Synced". If it still stops at "Receiving 4 of 4…" after 22 s, something after the last batch is holding it. The next things to read are the fold after it and `listOwnOnce`.

## 3. Flaky `smoke.spec.ts:1377` in WebKit: "Not a reference name. Did you mean Welwitschia mirabilis?"

Reproduced in Chromium. The test waited only for the name service's answer to "Welwit", then pressed Enter. But the catalogue's search also answers "Welwit": it reads it as the start of a genus and offers Welwitschia mirabilis, a suggestion in the menu.

On Enter, the field arms and checks the name (`checkExact`):
- the name service has already failed (502 here, as in the owner's run), so the check concludes "not reached";
- with a reference row near what was typed, the line becomes `nearest`: "Not a reference name. Did you mean Welwitschia mirabilis? Otherwise Add keeps exactly what you typed."

Read every 100 ms after Enter in Chromium, the line was "…Pick a name from the list…" for the first read only, and "Did you mean" for the next nine.

So the test passed by catching the moment before the check answered, which WebKit under load did not give it. The code means the settled line: a nearer name is offered by name (round sixty's `nearest`), and "Pick a name from the list" is the line when nothing is near. The test's comment, "a genus fragment matches nothing local", stopped being true when the catalogue search began matching a genus by its start.

**Fix (the test).**
- It now waits for both answers and for the suggestion, presses Enter, waits for the check's pill, then expects "Did you mean Welwitschia mirabilis?".
- A second case, "Qzxwv", which nothing in the reference is near, expects "Pick a name from the list" once the check has answered.
- Both still require that nothing is filed.

It passes in Chromium three times out of three. The code is unchanged.
