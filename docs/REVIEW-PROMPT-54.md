Your job is to check that the answers are right and complete, and to find the transitions this round still did not cross. Reproductions, not impressions: a finding names a file and line, or a request and its answer, or a sequence of steps and what appeared.

## The rules the project holds itself to

A claim the code does not keep is a finding.

1. Every figure on a species page states its source. Nothing on a species page is written by a person or a language model: every sentence is a quoted passage, marked and credited, a figure with its source, or a labelled reading of a fixed rule. No AI images.
2. A refusal is not an absence. A source that did not answer is "not checked", never "none".
3. Nothing derived is smoothed, guessed or inferred beyond what the rule states.
4. The collection is the grower's alone: on the device, synced only if they set it up, encrypted so the server never reads it. No accounts, no analytics, no third-party scripts. `/about/how` lists every request the grower's own pages make; `/about/formats` states every format and rule. Both must be true of the code at this commit.
5. The log is the collection. Anything else the device keeps (a snapshot, an index, a cache) is a reading of the log and must be droppable without loss; and no reading of the log may ever write to the log.

## What changed in this round (look here hardest)

### 1. The snapshot (`src/lib/db/vault.ts`, `src/lib/db/collection.svelte.ts`, `tests/unit/fold-snapshot.test.ts`)

The fold snapshot now carries an inventory of every held stamp (`heldStamps`, from what `apply` returns) and re-judges all of them at each load; the parked changes are read back by key after every load so their Apply stands; a parked number change counts as "numbered" for the one-shape pass; `markParked` drops the fold in the vault; the parked set is saved and awaited by whatever parked; `arrivalsAfter` returns the fold counter from the same transaction as the tail and a load that finds it moved throws the snapshot away; the replace and the wipe are one transaction; the other tabs' notices are listened for before the load reads; the snapshot is keyed to the build as well as `FOLD_RULES`; the restore is in a try with every field checked; the tab's own writes move its catch-up frontier (`storeIn` returns the arrival number it took) so there is no `getAllKeys` over the log any more; `incomplete` is derived. The revival repair reads a record whole (`changesOfRecord`, by the `byRecord` index) for records the tail touches with an `importedOn` or a removal.

Questions:

- The counter-with-the-tail argument (`fromFold`: `foldGen()` is read, then `readFold()`, then `arrivalsAfter(f.seq)` returns `gen` from its own transaction, and a mismatch discards the snapshot). Find an interleaving of a replace, a displaced change, `markParked`, a `writeFold` from another tab and a load that still lays one log's rows over another log's fold, or that passes a stale snapshot through `writeFold`'s counter check. The vault's `writeFold` compares the counter inside its transaction; the collection's `saveFold` serialises state after the read but before the write; a tab's `catchUp` moves `lastSeq` from `storeIn`'s return value. Is `lastSeq` ever behind a row this tab has not folded, or ahead of one it has?
- The held inventory. `applyHere` removes from `heldStamps` every stamp in the changes it was given and adds back what `apply` returned as held. A held change that is fetched as due and found, by then, parked (the clock corrected meanwhile): where does it go? A held stamp whose change left the log (a replace): is it ever fetched again, and does `changesByKeys` dropping it leave anything wrong behind? Two tabs, each with its own `heldStamps`, one of which folds a due change first: does the other tab's catch-up fold it a second time, and is that harmless?
- The revival repair now runs over whole records for the tail's touched records only. Construct a legacy revival (tombstone, then `importedOn` only) whose tombstone and import stamp are both already in the snapshot and whose record the tail never touches: the whole-log fold would remove it on every load; the snapshot load never will. Is that a difference a grower can see, and does the repair's intent (round sixteen, 5) require it to run again? Say whether the repair should be retired into the fold as a versioned rule, and what that rule would be.
- The one-shape pass now consults `parkedByRecord`, which is filled by `readParked` after the fold. Confirm the order in `load()`: the pass runs after `readParked`. Then find a record whose number change is held (not parked) at load time and whose number the pass writes anyway.
- The snapshot is keyed to the build (`version` from `$app/environment`). What is that string in a `wrangler dev` session and in the e2e suite, and can two different deploys share it? What does a device that opens an old service-worker shell against a new build's snapshot do?
- `order` is never pruned and `DEPLOY.md` says so. At four hundred and fifty thousand changes, measure the load from the snapshot on a throttled phone profile now that `getAllKeys` is gone (round fifty-three's reviewer measured 11.3 s), and say where the remaining time goes.

### 2. The reference's products (`src/lib/dossier/products.ts`, `src/lib/server/dossiers.ts`, `src/lib/server/sheets.ts`, `src/lib/ui/index.svelte.ts`, the `/api/entries`, `/api/sheets` and `/api/search` routes, `src/hooks.server.ts`, `tests/unit/products.test.ts`)

The corpus id is a hash of the sorted product hashes, computed after the products are built. A manifest is adopted only when the index under its id can be read; otherwise the corpus held before stands (or, with none held, the legacy path answers under the index's own etag). An isolate holding no manifest heads the manifest path each minute. No legacy sheet file is read under a manifest. A product the bucket lacks is remembered as lacking for a minute. The client names the bucket count it hashed by (`&n=`); a count other than the one served is a 409, `no-store`, after which the client forgets the corpus, reads it again and rehashes once; a corpus read that failed is not kept for the page's life. The hook's cache-key validation reads the catalogue product. A query with no words prepares nothing; a shard whose exact pass finds nothing is tried over the whole index, prepared for that request and let go.

Questions:

- The live bucket still has no manifest. From the live site: `/api/corpus` reports `buckets: 32`; `/api/entries?b=05&n=64&c=<id>` is a 409 with `no-store`; `/api/entries?b=05&c=<id>` without `n` still answers (an older client). Confirm all three, and say whether an older service-worker shell (which does not send `n`) can be harmed by anything in this round.
- Build the products for the fixture corpus (`npm run dossier -- --index` in a scratch tree, or `buildProducts`) and serve them from a mocked R2 (`tests/unit/products.test.ts` has the harness). Then: the manifest for B lands while A is held, with B's index missing (A should stand); B's index arrives (B should be adopted within the minute); the manifest for B lands on an isolate holding nothing (the legacy path, under the index etag, never under B's id); B's manifest names a product file whose bytes are a different product (not verified by hash, by decision; say what that costs); a manifest with `files` missing (rejected by `isManifest`). Which of these leaves a cacheable answer under the wrong id for any length of time?
- The 409 path on the client. Walk `entriesFor` and `sheetsFor` with a context that remembered `{A, 32}`, went offline, came back to `{B, 64}`: how many requests, in what order, and does the second attempt hash under 64? Then the reverse: the server goes from 64 back to 32 (a corpus rolled back). Then two concurrent `entriesFor` calls both getting a 409 and both clearing the caches.
- The whole-index pass on a shard miss. `hasExact` runs over the shard; a miss prepares the whole index for the request. On a corpus of fifty thousand species, what does one miss cost in time and memory, is the prepared index let go, and can a burst of misses (a bot typing nonsense) exhaust an isolate? Is `searchWhole` cached anywhere by accident?
- The id now changes when any product changes. A `--index` run after a sheet-only dossier change: which files are rewritten (should be the changed sheet, the manifest, and every file under the new id directory, since the directory is new). Is "incremental" still a true word for it, and does `DEPLOY.md` say what a refresh now uploads?
