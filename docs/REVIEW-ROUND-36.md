# Review round thirty-six: the sync path read end to end

My own pass, not a reviewer's: the key derivation and sealing (`src/lib/sync/crypto.ts`), the server (`src/lib/server/sync.ts` and the four routes under `src/routes/api/sync`), the engine's push and pull (`src/lib/sync/engine.svelte.ts`), and the service worker. Read for what an attacker with the address, an attacker with a token, a flaky connection, and two devices at once could each do. Two things changed; four were considered and left, with the reasons below so the next reader does not re-open them.

## Changed

1. **A body without a length was read whole before it was measured** (`readBody`). The declared `content-length` was checked first, and the read was capped, but the cap was applied to the buffer after `request.arrayBuffer()` had collected all of it. A chunked body carries no length, so a holder of a token could have the Worker hold up to the platform's own request limit in memory to earn one 413. The routes authenticate before they read, so this needed a valid token, which bounds it to a vault's own holder; still, the read now goes chunk by chunk and stops, cancelling the stream, the moment the running total passes the cap. The test feeds a stream that throws if pulled past the cap: the old reader pulled it and failed with that error, the new one answers 413 after at most a handful of chunks. A chunked body within the cap is read whole and in order.
2. **A species page read before waited on the network without limit.** The shells are cache-first since round nineteen, because a fetch on one bar of signal neither succeeds nor fails for a long time. The species pages, the front page, `/about` and `/settings` are network-first with a cache fallback, and the fallback only came once the fetch failed, so the same greenhouse that opens a plant's page at once showed a blank tab for a species page the grower had already read. Now, when the cache holds a copy, the network gets four seconds; past that the held copy answers and the fetch is left to finish under `waitUntil`, so the cache has the fresh page for next time. A page never read waits as before, since there is nothing else to answer with. Settings keeps its network-first order for the units it is rendered in; served from the cache past the budget, it re-reads the units on hydration as it already did offline. The three unawaited `cache.put` calls that could reject on a full store now swallow that, as the fourth already did.

## Considered and left

3. **The token hash compare is a plain `!==`.** `authed` and `ensureVault` compare SHA-256("token:"+token) against the stored hash with string equality, which is not constant-time. A timing attack on it would need to produce tokens whose hash matches the stored one byte by byte from the front, which is a preimage search on SHA-256 over a 147-bit random secret: the same work as guessing the token outright. Workers offers `crypto.subtle.timingSafeEqual`, but Node's WebCrypto does not, so the tests would need a shim for a change that defends nothing. Left, noted.
4. **`storeOnce` is a head then a put, not a conditional put.** Two writers to the same name at the same instant both see nothing and both put; the last wins. Batch names carry the device, so two devices cannot share one; two tabs of one device sealing the same changes make the same plaintext fingerprint, and either copy opens with the key. A photograph pushed from two devices at once differs only in its IV, and either copy is the same pixels. R2's `onlyIf` could close the window, but the Workers binding's create-only form (`etagDoesNotMatch: '*'`) is not something I could verify from here, and a condition that misfires would turn every first write into a 409. The window hurts nothing today; left.
5. **The crypto.** A 30-symbol key from a 30-letter alphabet is about 147 bits; HKDF to one AES-256-GCM key and one HMAC key; random 96-bit IVs, which at the rates a collection produces are nowhere near the 2^32 messages where the birthday bound matters; AAD binds the vault id, the kind and the name, so a batch cannot be replayed under another name or a photograph under another id; a vault id is 26 base32 symbols of SHA-256("id:"+token), and the base32 encoding's bias is over symbols, not over the entropy behind them. The one soft spot was already known and recorded: an older photograph sealed without its name in the AAD still opens under the unnamed form. Nothing to change.
6. **The engine's refusal path.** A batch the server refuses (400, 409, 413) is halved to the change at fault, which is noted and stays in the outbox, and every later run tries it again. That is the designed behaviour (a refusal is not an absence), and the sync page shows the note. The remaining way to a 409 on one change is the server holding a different batch under the same name from the same device in the same hour with the same twelve-digit fingerprint, which is a 2^-48 event or a batch stored before the plaintext header existed and re-sent after a lost reply, a window that closed before any vault existed. Left.
